## ٢.٣ إنشاء المشروع على الخادم — الخطوات الحرفيّة

```bash
ssh mafia-prod
mkdir -p ~/aibot && cd ~/aibot
git clone https://github.com/<user>/aibot.git .        # مستودع عامّ — لا أسرار فيه أبداً
cp .env.example .env && nano .env                      # الأسرار تُكتب باليد هنا فقط
chmod +x deploy.sh
docker compose build && docker compose up -d
docker compose logs -f api                             # حتّى ظهور «listening on 4080»
```

`docker-compose.yml` يتبع نمطك القائم: `${VAR:?رسالة}` **بلا قيمة احتياطيّة** لكلّ سرّ، فغياب
السرّ يُفشل الإقلاع بصوتٍ عالٍ بدل أن يستبدله بقيمةٍ محظورة. (هذا بالضبط ما أنقذ مشروع المافيا
حين حاول `JWT_SECRET` الافتراضيّ التسلّل إلى الإنتاج.)

خدمات compose الخمس: `db` (postgres:16-alpine) · `redis` (redis:7-alpine مع `appendonly yes`) ·
`api` · `worker` (نفس الصورة، أمرٌ مختلف) · `web`.

## ٢.٤ الأسرار — ما يدخل `.env` على الخادم

```
NODE_ENV=production
DATABASE_URL=postgresql://aibot:***@db:5432/aibot
REDIS_URL=redis://redis:6379
JWT_SECRET=<32 بايت عشوائيّة>
MASTER_KEY=<32 بايت base64 — مفتاح تشفير أسرار المستأجرين. فقدانه = فقدان كلّ التوكنات>
VAPID_PUBLIC_KEY= / VAPID_PRIVATE_KEY=      # ثابتان، وإلّا فقد كلّ المشتركين إشعاراتهم
PUBLIC_URL=https://aibot.masaros.net
PLATFORM_AI_KEY=<مفتاح Gemini الخاصّ بالمنصّة — قرار ق٢>
```

**المفتاح الرئيس `MASTER_KEY` أخطر سرٍّ في المنصّة.** به تُفكّ توكنات واتساب لكلّ عملائك.
انسخه احتياطيّاً خارج الخادم (مدير كلمات سرّ)، ولا تضعه في git، وخطّط لتدويره (`05`).

## ٢.٥ نصّ النشر — العقد نفسه المُجرَّب

انسخ `deploy.sh` من `unified-mafia` وبدّل الأسماء. العقد بالترتيب:

1. `set -Eeuo pipefail` + `trap … rollback` — كلّ خطوةٍ قاتلة، والفشل يتراجع.
2. **نسخة احتياطيّة قبل أيّ لمس**: `pg_dump | gzip`، ثمّ **تأكّد أنّ الملفّ > ١٠ آلاف بايت** —
   فشل `pg_dump` الصامت يُنتج ملفّاً ضئيلاً، وبدون هذا الفحص تنشر فوق حالةٍ لا تُستعاد.
3. `git pull origin master` **في سطرٍ مستقلّ**، لا في أنبوب (الأنبوب يُخفي كود الخروج).
4. الرفض إن غاب `.env`.
5. **وسم الصور العاملة** `<svc>:rollback-<stamp>` **قبل** البناء — هذا ما يجعل التراجع فوريّاً.
6. `docker compose up -d --force-recreate`.
7. الترحيلات بـ`psql -v ON_ERROR_STOP=1` من heredoc مُتَماثِل (`ADD COLUMN IF NOT EXISTS`)،
   وعند الفشل **اطبع ما قالته القاعدة فعلاً** ثمّ تراجَع.
8. **بوّابة الصحّة هي التي تُقرّر النجاح** لا نهاية النصّ: `/api/health` حتّى ٣٠×١ ثانية،
   ثمّ فحصٌ منفصل أنّ الواجهة تردّ 200/307/308. «الخلفيّة حيّة» ≠ «الموقع يفتح».
9. تنظيف الصور مع **الإبقاء على آخر ثلاثة وسوم تراجع**.
10. طباعة الرابط الحيّ ومسار النسخة **وأمر التراجع الحرفيّ**.

> **فخّ مثبت:** تعديل `deploy.sh` من ويندوز ثمّ `git add` يخزّنه `100644` فيفقد صلاحيّة
> التنفيذ بعد `git pull` على الخادم، فيتوقّف النشر قبل أن يبدأ. بعد أيّ تعديل:
> `git update-index --chmod=+x deploy.sh` قبل الدفع.

> **فخّ ثانٍ خاصّ بهذه المنصّة:** عند النشر تسقط اتّصالات السوكِت لثوانٍ. لا مشكلة في الإنبوكس
> (يُعيد الاتّصال)، **لكن رسائل الويبهوك التي تصل خلال إعادة التشغيل تضيع** إن كانت المعالجة
> في العمليّة. لذلك تُكتب كلّ رسالة واردة في القاعدة ثمّ تُدفع للطابور فوراً — وإن سقط العامل
> فالمهمّة باقية في ريدِس. اختبر هذا عمداً في المرحلة السادسة.

## ٢.٦ النطاق `aibot.masaros.net`

**⚠️ النفق مُدارٌ عن بُعد.** `cloudpanel-tunnel` يقرأ إعداداته من لوحة Zero Trust، والملفّ
المحلّيّ `/etc/cloudflared/config.yml` **متجاهَل تماماً** — تعديله وإعادة التشغيل لا يفعل
شيئاً سوى انقطاعٍ ٦٠ ثانية لكلّ المواقع.

الخطوات (أنت وحدك تستطيعها — تحتاج دخول لوحة Cloudflare):

1. **سجلّ DNS:** CNAME باسم `aibot` → `b8f315ec-a311-4b7a-8891-7b9e37a43f73.cfargotunnel.com`
   (proxied ✅). لازمٌ لأنّ `*.masaros.net` عليه wildcard يخدم تطبيق MasarOS.
2. **Public Hostname** في Zero Trust → Networks → Tunnels → `cloudpanel-tunnel`:
   - `aibot.masaros.net` · Path: `*` · Service: `HTTP` → `127.0.0.1:3070`
   - **الترتيب حاسم:** هذا الإدخال يجب أن يكون **فوق** إدخال `*.masaros.net`، وإلّا ابتلعه الـwildcard.
3. **مسار الويبهوك أوّلاً** (إدخالٌ منفصل فوق سابقه):
   `aibot.masaros.net` · Path: `api/*` · Service: `HTTP` → `127.0.0.1:4080`
   فتصل نداءات ميتا والـAPI إلى الخلفيّة مباشرةً بلا مرور بـNext.
4. تحقّق: `curl -I https://aibot.masaros.net` و`curl https://aibot.masaros.net/api/health`.

**عنوان الويبهوك لكلّ عميل:**
`https://aibot.masaros.net/api/webhooks/wa/{tenantPublicId}` — معرّفٌ عشوائيّ غير قابل للتخمين
(26 حرفاً)، يُولَّد عند إنشاء المستأجر ويُعطى للعميل ليلصقه في لوحة ميتا الخاصّة به.
التوقيع يُتحقَّق بـ**App Secret الخاصّ بذلك المستأجر**، لا بسرٍّ عامّ.

## ٢.٧ النسخ الاحتياطيّ والاستعادة

- `pg_dump` يوميّ عبر cron إلى `~/backups/aibot/`، مع الإبقاء على ١٤ يوماً.
- **نسخةٌ خارج الخادم**: لابتوبٌ واحد في بيتٍ = نقطة فشل واحدة. أرسل النسخة المضغوطة يوميّاً
  إلى مخزنٍ خارجيّ (seafile عندك أصلاً، أو R2). بلا هذا، حادثٌ للجهاز = فقدان بيانات عملاء.
- نصّ استعادة مكتوب ومجرَّب مرّةً على الأقلّ. نسخةٌ لم تُجرَّب استعادتها ليست نسخة.

## ٢.٨ جاهزيّة الترحيل (قرار ق٣)

الهدف: نقل المنصّة إلى VPS بأمرٍ واحد حين يستحقّ الدخل ذلك. قواعدٌ تُحترم من اليوم الأوّل:

1. **لا مسار مضيف في الكود** — كلّ التخزين في volumes لها أسماء، أو في S3/R2 خلف واجهة.
2. **لا اعتماد على شبكة البيت** — لا `192.168.*` في أيّ إعداد.
3. **كلّ سرٍّ في `.env`** — لا ملفّات اعتماد مثبّتة بمسارٍ مطلق.
4. **الترحيلات في الكود** (drizzle) لا يدويّة في psql، فتعيد بناء القاعدة من الصفر.
5. **نصّ `migrate-host.sh`** يُكتب في المرحلة السادسة: `pg_dump` + نسخ volumes + `docker compose up`
   على المضيف الجديد + تبديل الـPublic Hostname. الهدف: زمن تعطّل أقلّ من ١٥ دقيقة.
